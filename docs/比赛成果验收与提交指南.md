## 最新修复与验收（2026-10-30，第三轮）

本节覆盖下方第一、二轮的历史结论。AI 五个原始子项现在全部本地比较通过；`ai_column_vector_index` 连续通过两次，原始 SQL 和预期结果没有修改。平台尚未验证本次提交，因此不能将其描述为已取得官方分数。

追踪官方 [666df298：HNSW 更新路径 VID 维护](https://github.com/oceanbase/seekdb/commit/666df298) 后，发现本地更新解析器只根据显式 SET 列判断是否刷新向量内部 ID。AI 依赖列更新会通过 BEFORE UPDATE 触发器将向量置 NULL，这条隐式更新路径漏掉 VID 刷新。普通向量表加一个复制向量的触发器也能复现：旧二进制连续两次更新后报 `Duplicate entry '10001-D'`，与模型服务无关。

修复后，存在 BEFORE UPDATE 触发器且带向量索引的表会刷新 VID，并恢复 SQL NULL 的增量维护记录，同时避免读取 NULL 或删除标记的 LOB。此前只跳过 NULL delta 的办法隐藏了这个问题，并造成原始 EXPLAIN 差异。现在原始预期 `4 / 15` 自然匹配，没有硬编码估计值。该处理较保守：触发器存在时，无关字段更新也可能增加索引维护，但不会因此创建额外 AI 请求。

全文构建方面，借鉴官方 [f5674430：混合采样](https://github.com/oceanbase/seekdb/commit/f5674430a83f6bf1e3fe2af0204309eb63dbd907)，把 HYBRID_SAMPLE 从主倒排表扩展到文档词频辅助表和双向文档 ID 映射表。新增并行度 6 的建索引、更新、回滚和重建回归通过。此修改主要覆盖并行构建采样，不等于默认参数下必然提速。

本轮 Release 构建成功，17 个不同 mysqltest 比较通过：原始 AI 五项、向量连续重算/竞态/旧快照、新增普通触发器向量用例、NULL 转换、大向量失效，以及六项全文回归。原始向量用例另重复通过一次。

本轮修改前收到的平台结果仍是 AI 向量子项失败、全文零分：总建索引 17.009 → 17.509 秒，综合提升率 −6.7624% → −8.7702%；四类查询均变慢，命中数不变。这份反馈不能用于判断本次新提交是否通过。

同实例、同参数完整压测：总构建 38.439 → 35.129 秒（约缩短 8.6%）；中文/英文/混合查询分别为 4.2650 → 3.0990、5.8227 → 4.7294、4.1369 → 3.4967 ms。但 IK 双列构建 13.953 → 18.290 秒，BENG 分词 0.1358 → 0.1486 ms，LIMIT 查询 4.6122 → 8.2150 ms，存在明确回退。不能据此承诺综合分数转正，也不能把所有变化归因于并行辅助表采样。完整正负指标见 [性能记录](competition_fts_optimization.md)，原始数据见 [修改前](fts_trigger_sampling_before.txt) 与 [修改后](fts_trigger_sampling_after.txt)。

## AI COLUMN

本轮 AI 实现提交：`45a2aa4`，后续向量失效路径优化为 `dbbc926`。新增或修复的行为：

- `ALTER TABLE ... RETRY AI COLUMN` 支持状态和业务条件筛选、READY 行重算、零行命中；裸 `status` 是状态伪列，反引号包裹的 `status` 是业务列。
- 严格读取在每次执行时检查用户引用的 AI 列，包括缓存计划与优化器消除的表达式；PENDING 和 FAILED 报 11120。检查列的全部行，不能用 WHERE 只选 READY 行绕过。
- 后台任务使用持久化领取、租约与请求校验，模型调用在业务事务提交后执行；成功结果缓存，失败列有限重试。
- 同一行同次变更的 AI 列达到终态后，一个事务发布成功结果和 READY/FAILED 状态并清理任务。允许成功列与失败列一起发布；合法 NULL 结果仍可为 READY。
- ALTER ADD AI COLUMN 为已有行生成任务，重建包含所有 AI 列的触发器，保留已有列的结果。
- 禁止直接写入 AI 结果列的检查覆盖 INSERT SET、隐式列列表、ON DUPLICATE KEY UPDATE 和可更新视图。
- 向量失效保留 SQL NULL 增量维护记录，并为触发器隐式更新刷新 VID；NULL 不作为有效向量参加 ANN 检索。
- 更新/失效旧向量时，删除标记只使用旧向量 ID，不再读取最终不会写入的旧向量 LOB。2048 维、强制行外存储的回填/替换/删除/回滚回归通过。这是写入路径优化；第三轮 VID 修复后原始 EXPLAIN 比较也通过。
- 表名、数据库名中的反引号以及特殊主键在内部 SQL 中正确转义。
- AI 表的并行 DROP 与短事务结果发布使用一致的锁顺序，消除任务清理和发布之间的死锁；普通表仍使用并行 DDL。

## 全文索引调优

平台最新报告为 11.631 / 50 分，平均提升率为 +11.6309%；此前报告曾为 -7.3350%、-8.7702% 和约 -23.18%。不同轮次的查询耗时下降并不保证综合计分转正。旧文档把本机对固定基线的分数写成 100 分，不能证明代码带来的收益，已撤除该说法。

当前优化包括分词热路径减少重复转换/哈希操作，以及无需相关性分数的正向 MATCH 过滤跳过 BM25 计算。本次进一步加入经过原校验流程生成的默认配置缓存和按完整配置内容匹配的解析结果缓存，减少 TOKENIZE、建索引与查询中的重复 JSON 处理。需要分数的投影、聚合、排序、阈值判断、复杂布尔表达式和不兼容访问路径保留原路径。

后续五轮交替微基准中，执行两万次 TOKENIZE 的中位耗时：IK 从 1.556686 秒降为 1.440999 秒（约 7.4%），BENG 从 0.492396 秒降为 0.412735 秒（约 16.2%）。这不是正式评分基准。

完整基准仍有正负混合结果：建索引总耗时 34.154 → 32.822 秒，BENG 分词 0.1591 → 0.1402 ms；但 IK 分词、BENG 建索引及部分查询变慢，SELECT 1 也从 0.0744 → 0.1055 ms。共享环境下这些数据不能证明综合性能稳定提升，不能保证新版本官方非零分。完整数据均保留在性能文档和原始报告中。

优化是否有效以相同机器、相同参数、相同数据的前后配对测量为依据。测试数据、基准脚本和评分公式保持不变。测量记录与具体限制见 [全文检索优化记录](competition_fts_optimization.md)，正式成绩仍需平台重新评测。
