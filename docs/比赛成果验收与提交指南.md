## 六、AI COLUMN 题

### 已完成并验证

#### DDL 与元数据

- `CREATE TABLE ... AI COLUMN`。
- `ALTER TABLE ... ADD COLUMN ... AI COLUMN` 的解析、校验和元数据持久化。
- `sync_mode='async'` 和 `max_retries`。
- AI 函数、参数、结果类型、VECTOR 维度和链式依赖检查。
- 当前表、历史表和任务系统表。
- 隐藏 state/request/result-spec 列。
- `SHOW AI COLUMNS`。

#### 保护行为

- 拒绝 INSERT/UPDATE 直接给 AI 结果列赋值。
- 拒绝普通 DROP/MODIFY/CHANGE/RENAME/DEFAULT 绕过保护。
- 永久 DROP TABLE 时清理 AI 元数据和待执行任务。

#### DML 和事务联动

- INSERT 自动创建持久化任务。
- 同一行多个 AI 列共享 request ID。
- 批量 INSERT 逐行创建任务。
- 依赖列 UPDATE 使结果失效并重建任务。
- 无关列 UPDATE 不创建新任务。
- 主键 UPDATE 将任务谓词迁移到新主键。
- DELETE 清理任务。
- ROLLBACK 同时回滚业务数据和任务。

实测主键谓词格式符合测试预期：

```text
`id` = 2
```

### 当前未完成

以下能力没有达到可以声称完成的程度：

- 租户感知的异步模型 worker 和结果写回。
- `ALTER TABLE ... RETRY AI COLUMN ...`。
- `ai_column_strict_read` 的完整执行语义。
- 对已经存在的表执行 ALTER ADD AI COLUMN 后自动重建全部 DML 触发器。
- 多 AI 列结果的严格原子分组发布。
- AI 向量异步写回后的完整向量索引联动。

曾实现过一个定时 worker 原型，但实测发现系统内部连接看不到业务租户任务行，因此已经撤回。当前分支没有保留“能编译但不能工作”的实现。

### 需要参赛者注意

- AI COLUMN 当前最可靠的是 DDL、元数据、列保护和事务任务联动部分。
- 正式评测中，异步 worker、RETRY、strict read 和向量写回相关用例预计不能全部通过。
- 不要在提交说明中宣称 AI COLUMN 全部完成，应按上述完成范围如实说明。
