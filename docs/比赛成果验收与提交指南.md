## AI COLUMN

本轮 AI 实现提交：`45a2aa4`，后续向量失效路径优化为 `dbbc926`。新增或修复的行为：

- `ALTER TABLE ... RETRY AI COLUMN` 支持状态和业务条件筛选、READY 行重算、零行命中；裸 `status` 是状态伪列，反引号包裹的 `status` 是业务列。
- 严格读取在每次执行时检查用户引用的 AI 列，包括缓存计划与优化器消除的表达式；PENDING 和 FAILED 报 11120。检查列的全部行，不能用 WHERE 只选 READY 行绕过。
- 后台任务使用持久化领取、租约与请求校验，模型调用在业务事务提交后执行；成功结果缓存，失败列有限重试。
- 同一行同次变更的 AI 列达到终态后，一个事务发布成功结果和 READY/FAILED 状态并清理任务。允许成功列与失败列一起发布；合法 NULL 结果仍可为 READY。
- ALTER ADD AI COLUMN 为已有行生成任务，重建包含所有 AI 列的触发器，保留已有列的结果。
- 禁止直接写入 AI 结果列的检查覆盖 INSERT SET、隐式列列表、ON DUPLICATE KEY UPDATE 和可更新视图。
- 向量失效不再将 NULL 作为向量加入 delta buffer；回填、重算、删除和回滚通过额外 ANN 回归检查。
- 更新/失效旧向量时，删除标记只使用旧向量 ID，不再读取最终不会写入的旧向量 LOB。2048 维、强制行外存储的回填/替换/删除/回滚回归通过。这是写入路径优化，尚未消除原始 EXPLAIN 比较失败。
- 表名、数据库名中的反引号以及特殊主键在内部 SQL 中正确转义。
- AI 表的并行 DROP 与短事务结果发布使用一致的锁顺序，消除任务清理和发布之间的死锁；普通表仍使用并行 DDL。

## 全文索引调优

平台最新报告仍为 0 分，平均提升率为 -6.7624%，上一份报告为 -0.9889%，此前还有约 -23.18% 的报告。不同轮次的查询耗时下降并不保证综合计分转正。旧文档把本机对固定基线的分数写成 100 分，不能证明代码带来的收益，已撤除该说法。

当前优化包括分词热路径减少重复转换/哈希操作，以及无需相关性分数的正向 MATCH 过滤跳过 BM25 计算。本次进一步加入经过原校验流程生成的默认配置缓存和按完整配置内容匹配的解析结果缓存，减少 TOKENIZE、建索引与查询中的重复 JSON 处理。需要分数的投影、聚合、排序、阈值判断、复杂布尔表达式和不兼容访问路径保留原路径。

后续五轮交替微基准中，执行两万次 TOKENIZE 的中位耗时：IK 从 1.556686 秒降为 1.440999 秒（约 7.4%），BENG 从 0.492396 秒降为 0.412735 秒（约 16.2%）。这不是正式评分基准。

完整基准仍有正负混合结果：建索引总耗时 34.154 → 32.822 秒，BENG 分词 0.1591 → 0.1402 ms；但 IK 分词、BENG 建索引及部分查询变慢，SELECT 1 也从 0.0744 → 0.1055 ms。共享环境下这些数据不能证明综合性能稳定提升，不能保证新版本官方非零分。完整数据均保留在性能文档和原始报告中。

优化是否有效以相同机器、相同参数、相同数据的前后配对测量为依据。测试数据、基准脚本和评分公式保持不变。测量记录与具体限制见 [全文检索优化记录](competition_fts_optimization.md)，正式成绩仍需平台重新评测。
