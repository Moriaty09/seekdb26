# CPU/GPU 索引构建性能报告（2026-11-02）

最终候选已完成真实 ROCm 源码编译和 SQL 配对：公开 10K 样例的两轮构建加速几何平均为 5.401×，
查询为 2.253×；250K 合成输入的 128/256 维完整 SQL 构建加速分别为 3.076×、2.407×。
全部 GPU 配对中 Recall@10/100=1，检查的每条查询均返回 k 个互异合法 ID。
这些是本地开发结果，数据不是正式 SIFT250K/Hidden250K，不能据此宣称正式满分。

## 方法与计时边界

每个 GPU 版本使用全新服务目录，先 LOAD DATA 导入无索引表。
从固定 CREATE VECTOR INDEX 开始计时，到第一条固定近似查询取回合法结果；包含扫描、GPU 传输、
建图同步、持久化和首次重载，不包含编译、服务启动、生成真值或导入时间。
固定 GPU SQL/参数未修改：lib=cuvs、L2、hnsw、m=16、ef_construction=200、ef_search=64。

Top-10/100 各执行 4096 条单行 SQL，复用同一 libmysqlclient 连接；没有使用批量查询接口。
ID/Recall 检查在该组查询计时之后进行。配对数据、查询、环境、服务参数一致，并交换先后顺序。
所有有效测量都保留，未挑选较快轮次。显存采样读取所分配 GPU 的 PCI 0000:23:00.0 设备。

## 公开 10K 样例

输入来自模板 base.f32（10000×128）和 query.f32（100×128）；100 个独立探针循环至 4096 条 SQL。
原始 FP32 用 9 位有效数字往返导入，外部 ID=row_offset×17+1009，真值直接按 FP64 L2 距离计算。
该重复分布只用于本地诊断，不代表正式 4096 个独立查询。

| 顺序 | V5 GPU 构建＋首查 / s | 候选 GPU / s | 构建比 | 综合查询比 |
|---|---:|---:|---:|---:|
| V5 → 候选 | 8.697 | 1.368 | 6.359× | 2.265× |
| 候选 → V5 | 6.762 | 1.474 | 4.586× | 2.241× |

两轮比值几何平均：构建 5.401×、查询 2.253×。
基线构建存在明显波动，两次有效值均列出。两版 Recall@10/100 均为 1。
前一版 8 线程实验另存 thread-pair-1/2，不与最终 16 线程版本混算。

## 250K 合成输入：完整 SQL 链路

由 prepare_clustered_sample.py 生成：seed=20261102，16 个簇、16 维潜变量投影到 128/256 维并加入小噪声。
这是公开算法定义的独立合成压力输入，不生成、推测或替代隐藏数据。
每组 64 个独立查询循环至 4096 条 SQL，精确真值在计时外按实际 FP32 输入的 FP64 距离计算。
两组先后顺序分别为 V5→候选、候选→V5。

| 输入 | V5 构建＋首查 / s | 候选 / s | 构建比 | 综合查询比 | 两版 Recall@10/100 |
|---|---:|---:|---:|---:|---|
| LocalSynthetic / 250K×128 | 45.694 | 14.854 | 3.076× | 2.024× | 1.000 / 1.000 |
| LocalSynthetic / 250K×256 | 46.801 | 19.444 | 2.407× | 1.944× | 1.000 / 1.000 |

| 维度 | 实现 | Top-10 QPS | Top-100 QPS | Top-10 P95 / ms | Top-100 P95 / ms |
|---|---|---:|---:|---:|---:|
| 128 | V5 GPU | 143.725 | 138.444 | 7.313 | 7.653 |
| 128 | 候选 GPU | 299.818 | 271.740 | 3.359 | 3.766 |
| 256 | V5 GPU | 130.534 | 126.136 | 8.040 | 8.382 |
| 256 | 候选 GPU | 263.143 | 236.409 | 3.988 | 4.402 |

单独 bridge 的建图＋首查为 128 维 42.625→12.123 s、256 维 40.910→13.716 s。
该边界不包含 SQL 扫描/持久化/重载，不能替换上表的完整链路结果。

256 维首次本地试验在 LOAD DATA 阶段触发默认 SQL 超时，尚未开始 DDL；该次未产生构建成绩。
为两版统一设置导入会话超时 300 s 后，从新的空服务目录完成重跑；失败日志和成功结果同时保留。

## CPU VSAG 对比与回归

在同一最终候选进程中先创建独立 GPU 索引，再导入并建立 250K×128 CPU VSAG 索引，验证 OpenMP 初始化后的 CPU 功能。
CPU 表和查询输入与 128 维 GPU 配对相同。CPU DDL 使用 lib=vsag、m=16、ef_construction=200、ef_search=512；
GPU 保持固定 ef_search=64 的 SQL 配置。

| 实现 | 构建＋首查 / s | Top-10 QPS | Top-100 QPS | Recall@10 | Recall@100 |
|---|---:|---:|---:|---:|---:|
| CPU VSAG | 77.968 | 3914.627 | 2149.983 | 0.995313 | 0.985938 |
| V5 GPU | 45.694 | 143.725 | 138.444 | 1.000000 | 1.000000 |
| 候选 GPU | 14.854 | 299.818 | 271.740 | 1.000000 | 1.000000 |

CPU 与 GPU 的 Recall 和查询配置不同，表格展示实际取舍，不宣称严格同质量的 CPU/GPU 加速倍数。
CPU 结果不参与正式 GPU 计分。另有 10K、ef_search=64 的 CPU 回归：构建 2.669 s，
Recall 为 0.639917/0.652378，SQL 建表/建索引/查询均正常。

## 正确性、GPU 与资源证据

- Windows/Ubuntu 主机测试覆盖工作线程、并发、参数复位、分配错误、图视图释放、旧/新格式、损坏快照和 OpenMP 环境偏好。
- 真实 GPU 验证图导出/恢复逐边一致，修改恢复输入后索引仍有效，单查、批量、并发、持久化重载通过。
  近等距结果仅允许 FP32 舍入范围内的次序变化，严格保持 Top-k ID 集合相同及 k 个互异合法 ID。
- 普通 SQL 新快照重启、实际 V5 OBCUVS02 旧快照读取、新建 GPU 图及 CPU 索引均通过。
- 独立 rocprofv3 bridge 跟踪记录 2136 次 GPU kernel dispatch，
  其中 NN-descent 76 次、剪枝 1 次、CAGRA 搜索 421 次。

  普通环境再次重启/查询通过。不能据此宣称通过组织方完整 SQL GPU 抽检。
